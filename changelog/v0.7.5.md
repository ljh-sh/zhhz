## Added

- **`last_n_chars()` and `tail_n_chars()` helpers in `src/engine.rs`.**
  Borrow a `&str` for the prev context (last 1 char for bigram,
  last 2 for trigram), without allocating a combined String. No
  reverse-iteration char collection.

## Changed

- **`convert_segment` disambig branch rewritten.** Uses stack-allocated
  `[String; 4]` + linear dedup for `first_chars` (no Vec, no HashSet).
  Emits `pick + tail of cands[0]` directly — no `rest_of_first` alloc.
  Skips ngram entirely when both `prev_emit` and `out` are empty
  (start of input — no signal).

## Internal

The trigram hot loop's disambig branch was paying 6 small allocations
per multi-value match (combined String, first_chars Vec, seen HashSet,
rest_of_first String, prev_owned Option<String>, plus disambiguate()'s
2×N clones). Multi-value matches are ~0.2 % of FMM hits — but each
paid 6 allocs.

This release removes all 6.

## What didn't ship

- **zhhz#29 (byte-trie self-impl)**: not implemented. Spec lives on
  [zhhz#29](https://github.com/ljh-sh/zhhz/issues/29). Multi-week
  rewrite, cache-friendly node layout, expected +20-35 % on
  cache-cold corpora.
- **zhhz#30 (marisa-sys FFI)**: rejected. Implementation kept on
  `v0.7.4-marisa-trie` branch (pushed to origin) as reference; gives
  no measurable advantage on zhhz's data shape. See zhhz#33 for the
  decision record.

## Sample-based profile (from zhhz#32)

`sample` at 1 ms interval on macOS confirms zhhz is **CPU-faster than
opencc but wall-similar** because zhhz has 2× more idle time per
convert. zhhz CPU throughput on `realistic-var` is **133 MB/s vs
opencc's 67 MB/s**. The wall gap is cache + allocator behavior, not
CPU work.

`realistic-repeat`'s high zhhz stddev (2.83 MB/s) is explained by
cache-warm vs cache-cold variance — CPU time is more stable than wall.
