# zhhz v0.7.1

**zhhz fast path：realistic 中文 33 → 52 MB/s（+58%）。**
对 opencc 1.3.1：**0.50× → 0.80×**。

三个小分配器流量修复。无 API 变化，输出与 v0.7.0 字节完全一致。

## Bench（10 MB 中文，Apple Silicon，release）

| mode    | corpus   | v0.7.0 | v0.7.1 | Δ      |
| ------- | -------- | -----: | -----: | -----: |
| fast    | realistic| 33.03  | **52.32** | **+58 %** |
| fast    | worst    | 28.81  | **53.85** | +87 % |
| fast    | ascii-y  | 30.88  | 33.61  | +8.8 % |
| bigram  | realistic| 27.35  | 26.45  | -3.3 % |
| trigram | realistic| 27.01  | 27.12  | +0.4 % |

## 新增

- **I — `tail_2_chars` helper。** 把 `out.chars().rev().take(2).collect::<Vec<char>>()` 换成只分配结果字符串的字节切片遍历。
- **J — in-place stage buffer。** `convert_segment` 接收 `&mut String out`；链循环跨 stage 复用同一个缓冲区。
- **K — fast 路径跳过 `prev_emit` 分配。** 当 `ngram.is_none()` 时直接返回 `String::new()`，不算 `tail_2_chars`。

## 内部

- 新 `examples/bench_perf.rs` — 严格跑分 harness（3 个语料，best-of-5，丢弃 2 次预热）。

## 怎么找到的

`cargo install flamegraph` + macOS `sample` 显示热点是 `Vec<char>::from_iter` 每个 segment 跑两次 —— 10 MB 输入产生约 70 万次不必要的分配。

之前对 trie 结构做的 6 个 micro-opt 实验在 realistic 语料上都退步了（详见 zhhz#18 的完整列表）。

**教训：先 profile，再优化。** 凭直觉猜哪里是热点，每次都猜错。

## 注意

- 全部 45 个测试无需修改即通过
- API 不变，输出字节一致，无新依赖
- WASM 构建不受影响
