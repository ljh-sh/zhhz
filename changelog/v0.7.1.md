# zhhz v0.7.1

**zhhz fast path: 33 → 52 MB/s on realistic Chinese corpus (+58 %).**
vs OpenCC 1.3.1: **0.50× → 0.80×**.

Three small allocator-traffic fixes. No API changes, byte-identical
output to v0.7.0.

## Bench (10 MB Chinese, Apple Silicon, release)

| mode    | corpus   | v0.7.0 | v0.7.1 | Δ      |
| ------- | -------- | -----: | -----: | -----: |
| fast    | realistic| 33.03  | **52.32** | **+58 %** |
| fast    | worst    | 28.81  | **53.85** | +87 % |
| fast    | ascii-y  | 30.88  | 33.61  | +8.8 % |
| bigram  | realistic| 27.35  | 26.45  | -3.3 % |
| trigram | realistic| 27.01  | 27.12  | +0.4 % |

## Added

- **I — `tail_2_chars` helper.** Replaced `out.chars().rev().take(2).collect::<Vec<char>>()` with a single byte-slice walk that allocates only the result.
- **J — in-place stage buffer.** `convert_segment` takes `&mut String out`; chain loop reuses one buffer across stages.
- **K — skip `prev_emit` alloc in fast path.** Return `String::new()` without computing `tail_2_chars` when `ngram.is_none()`.

## Internal

- New `examples/bench_perf.rs` — rigorous bench harness (3 corpora, best-of-5, 2 warmup runs discarded).

## How we found it

`cargo install flamegraph` + macOS `sample` showed the hot spot was `Vec<char>::from_iter` running twice per segment — about 700 K unnecessary allocations per 10 MB input.

Six prior micro-opt experiments on the trie structure had all regressed on the realistic corpus (see zhhz#18 for the full list).

**Lesson: profile first, then optimise.** Source-level guesses about what is hot were wrong every time.

## Notes

- All 45 tests pass without modification
- API unchanged, output byte-identical, no new deps
- WASM build unaffected
